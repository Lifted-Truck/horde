# armor2-p5-nightly — the nightly runner frame (job list, runner, drill, freshness reader, check, workflow draft)

- **Queue item:** B448 phase 2 Wave 1, package P5 (ADR-209 item 4).
- **Why:** R1, R2 and R5 cannot count a nightly gate until something runs one, can fail, and says how old its last green was. This builds the frame only, so later packages (soak, deep fuzz, invariance matrix) add one `jobs.json` entry and nothing else; the workflow is a draft because the agent token cannot write `.github/workflows/`.
- **Evidence consulted:** `docs/strategy/blind-spot-armor-phase2.md` rows P5, P6 and "What runs where (P5)"; DECISIONS.md ADR-209 item 4; `.github/workflows/ci.yml` (house style, pinned SHAs); `tools/workflow_pin_check.py` (reused on the draft via `--paths`); `tools/stability_check.cpp` and `verify` lines 933-937; `tools/rtsan_check.py` and `tools/tsan_stress_check.py` (print SKIPPED and exit 0); `.kit/kit-gates.sh` `record()`; `tools/tolerance_registry_check.py`.
- **Alternatives rejected:** (1) Running `stability_check --seconds=14400` as the proposal names: the check holds the default patch's render plus three copies, so peak memory is linear in the run length; measured 474 MB RSS at 600 s on the dev Mac, so about 11 GB at 14400 (extrapolated, not measured) against a 16 GB hosted runner. The job runs 3600 s until P6 measures or the check stops holding the render. (2) Calling `record` from `verify nightly`: it overwrites `.harness/last-verify.json`, which the push gate reads. (3) A timeout inside the runner: a clock would decide pass or fail. (4) Drill that also runs the real jobs: hours of cost, no extra proof. (5) Keeping the name `LIMIT_HOURS`: `tolerance_registry_check` read it as a comparison tolerance and went red; registering it needs `docs/armor/` (out of scope), so the 48 h ruling is named `MAX_AGE_HOURS` and the lead may register it instead.
- **Verify:** `./verify fast` exit 0 (`.harness/last-verify.json`: target fast, exit 0, git 27047c2 = the base commit, run before the commit). `tools/nightly_check.py` is wired by one added line in `verify` after `test_table_check.py`, per the lead's amendment; the `nightly)` target is left to the lead.
- **Open questions:** the cron time, runner memory and speed, `brew install llvm` and the macOS sanitizers on GitHub's runners, and whether macOS minutes are free are all unverified (nothing ran on GitHub). The two macOS jobs (rtsan, tsan stress) were added beyond the single job the brief asked for, so the macOS leg judges something; they run through `legacy_gate.py` so a SKIPPED is recorded as skipped. The runner treats a night where nothing ran as red; that tightening is mine, not in the brief.
